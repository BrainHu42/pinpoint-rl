# Experiment plan: LLM-generated search queries for geolocation

Status: proposed for review; not implemented or run.

## Research question

Can Qwen3.5-4B turn visual clues and geographic hypotheses into natural-language search queries that acquire
useful evidence beyond whole-image retrieval and improve its final geolocation prediction?

The long-term goal is an RL agent that learns what to search for, how to interpret new evidence, and when to stop.
Its final answer can be an initial candidate, a newly retrieved image's location, or any other latitude/longitude.
This first experiment tests a fixed search loop using an existing model, without new SFT or RL training.

## Relationship to previous results

`LEARNINGS.md` records weak results from SigLIP2 text retrieval of confident place names supplied by Gemini.
That test did not evaluate targeted visual-clue queries generated by our model or their downstream usefulness
in a query → retrieve evidence → revise prediction loop. We will retain that negative evidence when interpreting
this experiment, rather than assume natural-language retrieval will work.

SigLIP2 is an offline text-to-image search backend. It does not simulate factual web snippets, exact entity search,
Wikipedia articles, or the coverage of live search engines. Success supports this offline acquisition mechanism;
failure does not settle the usefulness of live search. Google/Wikipedia providers and adapters remain undecided.

## Model and inputs

- Use the best available existing Qwen3.5-4B SFT checkpoint, thinking off. Verify checkpoint availability first;
  record the exact checkpoint and decoding settings. If unavailable, make the substitution explicit before running.
- Give every arm the same query photo and the same initial pooled candidate locations and retrieval statistics.
- Generate an initial prediction before showing additional evidence.
- Train no new model and use no Gemini-generated queries or supervision for this experiment.

## Search strategies

Evaluate two strategies separately, each producing three short, distinct queries:

| Strategy | Example | Purpose |
|---|---|---|
| Visual clues | baseball stadium with fountains behind the outfield | Search observed appearance without committing to a location |
| Geographic hypotheses | Kansas City baseball stadium outfield fountains | Seek evidence for a possible location |

Record the clue or uncertainty behind each query, and distinguish observed sign text or entities from inferred
names. Do not use ground-truth coordinates or labels to formulate queries or select evidence. Keep queries within
the text encoder's supported input length; record token counts and any truncation. Freeze the exact generation
prompt and decoding settings after the development stage.

## Fixed acquisition loop

1. Generate three queries from the original photo and initial candidates, before receiving search results.
2. Embed each query with `google/siglip2-giant-opt-patch16-384` and search both MP16 and OSV-5M galleries.
3. Return one image per corpus per query: six evidence images in total. Retrieve deeper ranked lists internally
   to replace duplicates or unreadable results. Log any unfilled slots rather than silently changing the budget.
4. Show the evidence cards alongside the original photo and initial candidates. Each card contains the image,
   its published coordinates, corpus, and originating query. Treat its coordinates as a hypothesis, not proof.
5. Ask the same model for a revised latitude/longitude, without restricting it to any candidate list.

Use fixed corpus allocation initially. Adaptive querying, source selection and stopping belong to the later RL
experiment. Cache queries, raw search rankings, selected cards, original and revised answers, and model settings.

## Experimental arms

| Arm | Additional evidence |
|---|---|
| No search | None; original prediction baseline |
| No-evidence revision | Ask the model to revise without new evidence; controls for another answer opportunity |
| Extra whole-image retrieval | Six additional images from the original image query |
| Caption search | Six images retrieved with one general caption: three per corpus |
| LLM visual-clue queries | Six images from three targeted visual queries: one per corpus per query |
| LLM geographic queries | Six images from three hypothesis-conditioned queries: one per corpus per query |

All evidence-bearing arms use the same six-image budget, thumbnail sizes, evidence-card format, final-answer
instructions and decoding settings. The whole-image arm uses the same three-per-corpus allocation. Deduplicate
within each evidence package and exclude any reference images already shown to the model. Log overlap with
the initial retrieval results, even when those images were not previously shown. Retrieval depth and generation
costs differ across arms; report them rather than claim identical total compute.

## Data and exclusions

- Start with approximately 200 held-out MP16 validation photos, split by photographer, for development and
  plumbing checks. Do not train on these photos.
- Exclude each query image, same-photographer MP16 gallery images, and known duplicates from returned evidence.
  Apply existing benchmark leakage and burned-in GPS overlay rules.
- OSV-5M lacks photographer ids; record this limitation and apply available duplicate/sequence exclusions.
- After freezing prompts, budgets and metrics, evaluate on the full im2gps3k and yfcc4k eval halves (3,795 queries
  in the documented caches). Report actual evaluated counts and failures. These halves have informed earlier
  research decisions and are not a fresh final test.
- Keep Wikimedia untouched for final validation once its loader is implemented.

## Measurements

Primary outcome: greedy accuracy within 25 km. Secondary outcomes: accuracy within 1 km and geographic error.
Report paired differences and 95% confidence intervals, both pooled and separately for each benchmark.

Additional diagnostics:

- Added candidate coverage: correct coordinates among initial candidates plus acquired evidence locations,
  compared with the initial list and the extra whole-image arm, at 1 km and 25 km.
- Corrections versus regressions: initial wrong → final right and initial right → final wrong.
- Evidence usefulness when a correct candidate was already present.
- Successful final predictions outside the initial candidate set, with distance-based definitions fixed in advance.
- Query quality: generic, repeated or hallucinated queries; irrelevant retrieved images; readable-text and
  distinctive-landmark slices. Manually inspect a fixed sample of successes and failures.
- Cost: query generation and answer tokens, evidence image tokens, gallery search time, inference latency,
  and failed or incomplete calls.

Candidate coverage is a diagnostic, not deployable accuracy. Evidence can help without being geographically
near the truth, and geographically nearby results can still mislead the model. Evaluate actual final predictions.
Do not use ground truth to pick results, queries, or a best answer at inference time.

## Proposed continuation gate

Before full evaluation, lock a primary query strategy using the MP16 development set; treat the other strategy
as a secondary comparison. This avoids choosing the best strategy after looking at benchmark results.

Continue toward adaptive acquisition if the primary strategy improves accuracy within 25 km by at least
2 percentage points over extra whole-image retrieval, with a paired 95% confidence interval excluding zero,
and no material regression within 1 km. Define the acceptable 1 km regression margin during development and
freeze it before benchmark evaluation. Also report improvements over no search, no-evidence revision and caption
search; if caption search performs equally well, targeted query generation has not demonstrated extra value.

Interpret possible outcomes:

| Result | Implication / next step |
|---|---|
| Targeted search beats controls in final accuracy | Test adaptive query selection and stopping, then RL |
| Evidence coverage improves, final accuracy stays flat | Investigate evidence interpretation before training acquisition |
| Caption search matches targeted queries | Simple description retrieval may be sufficient; targeted querying is unproven |
| Extra whole-image retrieval matches targeted queries | Additional evidence may help, but natural-language querying adds no demonstrated value |
| Neither useful evidence nor accuracy improves | Reassess this SigLIP backend or query strategy; live entity/web search remains a separate question |

## Implementation and prerequisites

Add a dedicated experiment module with resumable `generate`, `retrieve`, `answer` and `report` stages. Reuse:

- `experiment/query_headroom.py`: SigLIP2 text embedding, gallery search and geographic clustering utilities.
- `experiment/evidence_test.py`: evidence-card construction and exemplar image handling.
- `experiment/sft_data.py`: MP16 image reader and held-out query pool.
- `data/benchmarks.py`: benchmark loading and geographic metrics.

Finish and validate MP16 and OSV-5M embedding caches, then build the required neighbour/candidate caches before
full evaluation. Verify original image access for both corpora. Configure multi-image serving for the query photo
plus six evidence images and check context length and GPU memory on the development set. The existing one-image
SFT/GRPO configuration does not implement this experiment.

Keep the search request interface independent of the backend: raw natural-language query, source, result budget,
and provenance. Preserve raw queries so a future Google or Wikipedia adapter can accept them without treating
SigLIP's preprocessing or similarity scores as web-search behavior.

The immediate deliverable is a reproducible report of search queries, acquired evidence, actual prediction gains,
failure modes and costs. New training and live API integration are follow-up decisions based on that report.
